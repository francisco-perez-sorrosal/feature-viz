# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An educational, POC-grade reimplementation of three ideas from Distill's *Circuits* thread (2020). A small library (`feature_viz`) holds all the logic; four [marimo](https://marimo.io) notebooks are thin interactive wrappers over it. The first three each map to one Distill article: `zoom-in` (what a neuron is), `visualizing-weights` (kernels between neurons), `early-vision` (the synthesised feature-visualisation image). The fourth composes 01 + 02 into a one-hop **circuit** view — Claim 2 of *Zoom In* made concrete. Clarity of the demonstration is the product — not coverage or performance.

## Commands

```bash
uv sync                                              # create .venv, install deps + feature_viz (editable)
uv run marimo edit notebooks/01_neurons_and_features.py  # open a notebook in the reactive editor
uv run marimo run  notebooks/03_feature_visualization.py   # read-only app view
uv run python -c "import feature_viz as fv; ..."     # use the library headlessly
```

No test suite, no linter config, no CI exist. Do not invent test/lint commands. To validate a notebook headlessly after editing, export it — this executes every cell: `uv run marimo export html notebooks/<nb>.py -o /tmp/check.html`.

`uv` is the only supported workflow. There is no `requirements.txt` and no plain `pip` path — `pyproject.toml` is the single source of dependency truth.

## Architecture

Two layers, strict direction: notebooks import the library; the library never imports a notebook.

- **`src/feature_viz/`** — installable package (src-layout, hatchling build). Modules: `device` (device probe), `model` (InceptionV1 loading + activation hooks; `get_layer` resolves dotted names like `inception3b.branch2`), `neuron` / `weights` / `feature_vis` (the three concepts), `dataset_examples` (receptive-field crops at each neuron's firing peak — `top_examples` per channel, `channel_cards` for the scout), `plotting` (matplotlib helpers; `show_circuit_rows` is the per-input row used by notebook 04). `__init__.py` re-exports the public API.
- **`src/feature_viz/sample_images/`** — ~196 bundled ImageNet sample images (package data) for notebook 01's dataset-example view. Regenerated by `scripts/fetch_sample_images.py`; provenance + licensing in that directory's `README.md`. ImageNet samples — non-commercial educational use only.
- **`notebooks/`** — marimo notebooks, one per Distill article. Plain `.py` files (not `.ipynb`): reactive-cell apps, git-diffable, agent-editable with normal tools.

Conventions across the package:

- **Model**: `torchvision.models.googlenet` + `GoogLeNet_Weights.IMAGENET1K_V1`, always `.eval()`. `load_inception()` freezes parameters by default — the feature-vis loop optimises the *input image*, never the weights. Layers are GoogLeNet *named modules* (`inception3b`, `inception4b`, ...); activations are read via the `capture_activation` context manager (hook always removed on exit).
- **Channel-index caveat**: faithful InceptionV1 re-implementation, but channel indices do **not** match OpenAI Microscope's TensorFlow checkpoint. Structural/algorithmic claims carry over; specific neuron numbers do not.
- **`render_neuron`** returns a `RenderResult` (final uint8 image + per-step activation curve + optimisation `snapshots` when `n_snapshots > 0`) and accepts a `progress` callback — notebook 03 uses snapshots for its evolution filmstrip; the function does no file I/O.

## Device selection — non-obvious, do not "simplify"

`device.best_device("auto")` runs `probe_mps_render()`, which tests the *actual* feature-vis op set on MPS — the FFT round-trip **and** `grid_sample` backward — forward and backward, before selecting a device.

On an M2 with PyTorch 2.12 this resolves to **CPU**, and that is correct, measured behaviour:

- The FFT path (`irfft2`) works on MPS.
- `grid_sampler_2d_backward` (the rotation in `random_transform`) is unimplemented on MPS. With `PYTORCH_ENABLE_MPS_FALLBACK=1` it round-trips to CPU per step — measured *slower* than plain CPU (112 vs 70 ms/step). Even with rotation removed, MPS beats CPU only ~1.14×.

The probe is intentionally a *runtime* check, not a hard-coded `cpu`: if a future PyTorch implements the missing op, MPS is selected automatically. Do not replace the probe with an assumption, and do not add the `PYTORCH_ENABLE_MPS_FALLBACK` workaround — it was measured and rejected.

## marimo specifics

- A variable may be defined in only one cell (reactive single-definition rule). Cell function args are inbound dependencies; the return tuple is outbound.
- Expensive cells are gated behind `mo.ui.run_button` + `mo.stop(...)` — notebook 03's ~18 s render must not auto-run on every control change. Preserve this pattern when editing.
- Notebooks are validated by `marimo export html` (executes all cells); a gated render cell stays gated during export, so export is fast.
- **`mo.md()` formatter gotcha**: a cell whose whole body is `mo.md(...)` gets rewritten by marimo's formatter into a triple-quoted block. Always pass a *single* triple-quoted string (`mo.md(r"""...""")`) — implicit string concatenation (`mo.md("a" "b")`) is mangled into literal stray `"` characters. Nested `mo.md(...)` inside `mo.vstack`/`mo.callout` is exempt (not reformatted).
- Concept explanations use `mo.accordion` (collapsible reveal); `<abbr>` hover tooltips do **not** survive marimo's markdown renderer. Diagrams use `mo.mermaid` (source lives inline in the notebook `.py`).

## Intentional approximations (preserve them)

The README's "What this skips" is deliberate scope, not omissions to fix: `feature_vis` does not fold BatchNorm (only `weights` does); `effective_kernel` ignores the ReLU between the `1×1` and `k×k` convs (the same approximation the Distill paper makes); no diversity term or frequency-band curriculum from the *Feature Visualization* paper. For production-grade work the README points to `lucent` / `lucid` — this repo stays minimal on purpose.
